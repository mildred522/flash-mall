# Flash Mall 性能测试指南

## 测试目标

性能套件同时回答四个不同问题，不能用一次高并发请求代替：

| 类型 | 要回答的问题 | 当前全量配置 |
| --- | --- | --- |
| 基准 | 低负载延迟是否可重复 | 公开读 100 TPS、订单 2 TPS、完整交易 1 TPS，各 3 轮 30 秒 |
| 负载 | 预期工作负载是否满足 SLO | 公开读 600 TPS、订单 10 TPS、完整交易 3 TPS，各 60 秒 |
| 饱和 | 不受目标速率限制时最多能完成多少业务场景 | 读链路从并发 32、订单与完整交易从并发 8 自动倍增；首次 SLO 失败或连续两档成功业务 TPS 增长不足 5% 后停止 |
| 压力 | 满足成功率和尾延迟 SLO 的容量边界在哪里 | 目标 TPS 自动倍增到首次失败，再二分收敛到约 10% 区间；读、订单、完整交易分别设安全上限 |
| 稳定性 | 持续流量下是否退化或增长资源 | 500 TPS 公开读、5 TPS 订单和 1 TPS 完整交易并行 5 分钟 |

`read` 是 70% 商品目录、20% 商品详情、10% 店铺详情的真实流量配比。`trade-cycle` 依次经过商品目录、商品详情、创建订单、创建支付、沙箱确认、支付状态查询和订单详情查询，覆盖 Hertz、Order RPC、Product RPC、Inventory Kitex、MySQL、Redis 与支付回调编排。登录只在阶段开始前执行一次，模拟正常会话，不把重复登录混入交易容量。

恢复阶段另行验证正常支付、同幂等键重放、RabbitMQ 暂停期间支付、Outbox 恢复排空和最终业务不变量。压力/饱和档的成功率或延迟失败用于发现边界，不单独判整套失败；阶段结束后无法恢复的悬挂预占、未完成库存确认或缓存不一致仍属于异常失败，必须阻断结果，不能用“压力测试允许失败”掩盖。

## 吞吐口径

- `business TPS`：每秒完成的业务场景数。读场景一次一个请求，订单场景一次包含创建和取消，完整交易一次包含七个请求。
- `HTTP QPS`：所有场景步骤实际发出的 HTTP 请求总数除以阶段总耗时，用于观察网关和下游服务承受的真实请求吞吐。
- `target TPS`：开放模型计划注入的业务场景速率；达到目标速率、成功率和 p95/p99 才算该档通过。
- 饱和扫描使用闭环模型，不设置目标 TPS；平台期按成功完成的业务 TPS 计算，不按包含失败子请求的 HTTP QPS 计算。报告取观测到的峰值，而压力扫描给出最后通过与首次失败区间。两者必须同时看，不能用单个固定档位冒充上限。

## 安全边界

- 只能向 `127.0.0.1`、`localhost` 或 `::1` 发起有副作用的测试。
- 必须同时传入 `--allow-mutation` 和 `--confirm-reset`。
- 套件开始和结束都会恢复固定演示夹具，上传素材卷不参与重置。
- 套件临时通过管理员库存调整接口把商品 100 扩为 1,000,000 件，避免演示库存先于服务容量耗尽；结束时恢复固定夹具，不直接改 Redis 或数据库绕过业务边界。
- 负载生成器运行在 Compose 网络内，避免 Windows 端口转发和 WSL 时钟调度污染吞吐结论。
- 每个负载容器带独立运行标签，退出时只清理本次测试产生的容器。
- 写阶段结束后通过正式取消接口释放未支付订单，并等待已支付订单的库存确认恢复任务排空；Redis 可用库存按 MySQL 桶库存减活动预占校验，另行核对预占总量键。
- 性能套件把链路追踪采样率临时降为 1%，避免 Jaeger 成为被测系统瓶颈；退出和异常中断都会恢复日常默认 10%。

## 执行方法

在 Ubuntu WSL 的项目目录执行：

```bash
# 约几分钟，用于检查测试链路本身
scripts/perf/run-performance-suite.sh \
  --suite quick --allow-mutation --confirm-reset

# 约 20–35 分钟；自动扩档数量取决于本机实际容量
scripts/perf/run-performance-suite.sh \
  --suite full --allow-mutation --confirm-reset
```

结果保存在 `.runtime/performance/<运行时间>/`：

- `report.md`：适合人工阅读的阶段结果与瓶颈结论；
- `summary.json`：完整机器可读结果；
- `stages/*.json`：每一档的业务 TPS、HTTP QPS、操作和七步交易阶段延迟；
- `resources-*.tsv/jsonl`：容器、MySQL、Redis 和主机资源时间序列；
- `profiles/<压力档>/`：Hertz、Order RPC、Product RPC、Inventory Kitex 的 CPU profile 与 top；
- `invariants.json`：重复订单、重复支付回调、负库存、悬挂预占、Outbox 和 Redis/MySQL 库存一致性结果。

只有通过的完整结果才能用 `freeze-performance-result.mjs` 固化到 `benchmarks/results`。

## 当前冻结结果

正式结果绑定提交 `ab99259bb847db10bbb00c45fef7407cd52657ff`，环境为 4 vCPU、约 7.76 GiB 的 Ubuntu WSL Docker Engine，夹具为 `20260730_demo_fixture_v1`。

- 公开读：600 RPS 预期负载实际 599.99 QPS，p95 0.376 ms；压力最高测到 3000 RPS，实际 2999.93 QPS、全部成功、p95 0.476 ms，尚未观察到失败边界。
- 订单生命周期：10 RPS 预期负载实际 9.99 QPS、全部成功、p95 139.773 ms；25 RPS 压力档通过，40 RPS 首次失败，边界位于 25–40 RPS。
- 40 RPS 订单档的 `create_order` 是主导步骤，整体 p95 2943.442 ms，MySQL `Threads_running` 峰值为 8；Hertz、Order RPC、Inventory Kitex 都没有 CPU 饱和，因此优先排查事务编排、数据库连接等待和 DTM 分支开销，而不是先扩网关。
- 5 分钟稳定性中，500 RPS 读与 5 RPS 订单均 100% 成功；Redis 无阻塞客户端，MySQL 无当前行锁等待，主机可用内存没有持续下降。
- 将 Trace 默认采样率从 100% 调整为 10% 后，Jaeger 同一稳定性阶段内存增长由旧轮次的 406.5 MiB 降至 37.4 MiB，低于 128 MiB 稳定性门禁。
- 支付、40 次同幂等键重放和 RabbitMQ 暂停恢复均通过；最终重复订单、重复支付回调、负库存、悬挂预占、未完成库存确认、Outbox 残留和 Redis/MySQL 库存差异全部为 0。

冻结证据为 `benchmarks/results/performance-20260815.json`。这些数字只描述当前提交、固定数据和本机 Compose 资源，不代表公网生产容量。

## 如何定位瓶颈

1. 先区分 `business TPS`、`HTTP QPS` 和 `target TPS`，再看成功率、丢弃数和 p95/p99，避免把多请求业务循环当成单请求 QPS。
2. 再看 `steps`，把完整交易拆为浏览、创建订单、创建支付、确认支付和终态查询，找到尾延迟的业务阶段。
3. 对照同一阶段的容器 CPU/内存、MySQL 活跃线程与行锁、Redis 阻塞和主机内存。
4. 使用该压力档自动采集的 pprof 判断 CPU、锁竞争、网络等待或数据库调用占比。
5. 对照饱和扫描的峰值和压力扫描的最后通过/首次失败档；若只到达安全上限而未失败，报告必须明确写“边界尚未观察到”。
6. 最后用 Jaeger 定位单请求跨度；Trace 用于解释瓶颈，不用 100% 采样制造新的瓶颈。

## 失败分类

- **预期边界失败**：压力或饱和档首次出现成功率、p95/p99、生成器丢弃或网关过载；它定义上界，扫描应立即停止或向通过区间二分，不继续无意义放大。
- **异常业务失败**：阶段流量结束后仍有悬挂预占、已支付但库存未确认、Outbox 未排空、负库存或 Redis/MySQL 不一致；无论它出现在什么压力档，都必须修复并使套件失败。
- **异常测试失败**：冷启动导致基线漂移、观测组件占满资源、夹具库存不足、以 HTTP 子请求数冒充业务吞吐等；这类结果不能用于项目容量结论，应修正方法后重跑。
