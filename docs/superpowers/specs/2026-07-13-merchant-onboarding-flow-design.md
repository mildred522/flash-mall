# 商家注册与入驻闭环设计

## 目标

在独立商家后台 `/merchant` 内补齐“注册普通账号、提交商家入驻申请、查看审核状态、管理员审核、审核通过后进入经营后台”的完整图形化流程。第一阶段只实现简易可用版，不增加营业执照、资质图片、经营类目、实名开户或商家切换能力。

## 当前基础与缺口

项目当前已经具备以下后端能力：

- 普通用户注册和密码登录；
- `POST /api/merchant/apply` 创建商家入驻申请；
- `GET /api/admin/merchants/applications` 查询申请列表；
- `POST /api/admin/merchants/applications/audit` 审核申请；
- 审核通过时创建 `merchant`，并建立 `merchant_user` 的 `owner` 绑定；
- `GET /api/merchant/me` 查询当前账号绑定的商家。

当前缺少：

- 商家后台注册界面；
- 本地演示验证码的安全展示；
- 当前用户申请状态查询接口；
- 未申请、待审核、已驳回、已停用等状态页面；
- 管理员商家入驻审核页面；
- 审核通过后从入驻流程切换到经营后台的完整前端分流。

## 产品范围

### 本期包含

- 商家后台手机号、验证码、密码注册；
- 商家名称和联系电话入驻申请；
- 当前申请状态、申请编号、审核备注和时间展示；
- 待审核状态恢复；
- 驳回后修改资料并重新申请；
- 管理员申请列表、状态筛选、通过和驳回；
- 审核通过后自动进入商家经营后台；
- 商家停用状态提示；
- 本地环境动态调试验证码展示；
- 直接相关的自动检查和一次 Chrome 真实链路验收。

### 本期不包含

- 营业执照、资质图片和实名信息；
- 经营类目、开户地址和协议签署；
- 申请撤回和待审核资料修改；
- 一个账号管理多个商家或商家切换；
- 短信服务商接入；
- 商家审核通知、站内信或消息队列。

## 总体架构

沿用现有独立商家后台和 `MerchantGuard`，将守卫扩展为入驻状态分流器。守卫只负责查询、状态判断和页面切换，登录注册、申请填写和状态展示分别由独立组件完成。

状态流如下：

```text
打开 /merchant
    │
    ├─ 未登录
    │    └─ 登录 / 注册账号
    │              └─ 注册成功后自动登录
    │
    ├─ 已登录且已有有效商家绑定
    │    └─ 进入商家经营后台
    │
    └─ 已登录但没有有效商家绑定
         ├─ 绑定存在但商家停用：显示停用说明
         └─ 查询本人最近一次入驻申请
              ├─ 无申请：显示入驻申请表
              ├─ 待审核：显示申请资料和等待状态
              ├─ 已驳回：显示原因并允许重新申请
              └─ 已通过：重新查询绑定，绑定就绪后进入经营后台
```

商家状态页提供手动刷新，不使用定时轮询。注册、申请和审核接口成功后均由前端显式刷新对应状态。

## 前端组件

### MerchantAuthPage

替代当前只有密码登录的商家登录页，提供“登录”和“注册”两个标签页。

注册字段：

- 手机号；
- 动态验证码；
- 密码。

行为：

- 调用现有发送验证码和注册接口；
- 本地环境在发送成功后展示后端返回的动态 `debug_code` 和有效期；
- 发送按钮显示冷却倒计时；
- 注册成功后保存访问令牌和刷新令牌，直接触发身份重新检查；
- 验证码错误、过期、发送频繁和注册冲突显示明确中文提示。

### MerchantOnboarding

根据本人最近一次申请状态渲染：

- 无申请时的入驻申请表；
- 待审核状态页；
- 已驳回状态页和重新申请表；
- 已通过但绑定尚未可见时的初始化提示；
- 商家被停用时的联系平台提示。

申请字段：

- 商家名称，必填；
- 联系电话，默认使用注册手机号并允许修改。

驳回后使用上一条申请的名称和联系电话回填表单，新提交创建一条新的申请记录，旧记录继续保留。

### MerchantGuard

守卫维护以下状态：

- `loading`；
- `login`；
- `apply`；
- `pending`；
- `rejected`；
- `approved_initializing`；
- `disabled`；
- `authorized`；
- `error`。

守卫先查询 `/api/merchant/me`。存在有效商家时进入经营后台；仅存在停用商家时显示停用状态；没有绑定时查询本人申请。退出或切换账号时清理访问令牌、刷新令牌及内存中的入驻状态。

### MerchantApplicationsPage

统一管理员后台增加“商家入驻”菜单和页面，包含：

- 申请编号；
- 用户 ID；
- 商家名称；
- 联系电话；
- 状态；
- 申请时间；
- 商家 ID；
- 审核备注、审核人和审核时间。

页面默认将待审核记录置顶，支持全部、待审核、已通过和已驳回筛选。待审核行提供“通过”和“驳回”操作；驳回必须填写原因，通过备注可选。已处理记录不再显示审核操作。

## 后端接口

### 创建申请

保留：

```http
POST /api/merchant/apply
Authorization: Bearer <user token>
Content-Type: application/json

{
  "merchant_name": "测试商店",
  "contact_phone": "13800000003"
}
```

规则：

- 用户 ID 只能来自 JWT；
- 商家名称必填，联系电话需通过服务端格式校验；
- 已有有效商家绑定时拒绝再次申请；
- 已有待审核申请时返回该申请，不创建重复记录；
- 最近一次申请被驳回后允许创建新申请。

### 查询本人申请

新增：

```http
GET /api/merchant/application
Authorization: Bearer <user token>
```

存在申请时返回：

```json
{
  "application": {
    "apply_id": 12,
    "merchant_name": "测试商店",
    "contact_phone": "13800000003",
    "status": 0,
    "status_text": "pending",
    "merchant_id": 0,
    "audit_remark": "",
    "create_time": "2026-07-13 15:00:00",
    "audit_time": ""
  }
}
```

从未申请时返回：

```json
{
  "application": null
}
```

接口始终以 JWT 中的用户 ID 查询，不能接受目标用户 ID 参数。

### 管理员申请列表

扩展现有接口：

```http
GET /api/admin/merchants/applications?status=0&page=1&page_size=20
Authorization: Bearer <admin token>
```

响应包含 `items` 和 `total`。`status` 可省略，省略时查询全部；分页参数设置合理默认值和上限。排序规则为待审核优先，同一状态内按申请时间倒序。

### 管理员审核

保留：

```http
POST /api/admin/merchants/applications/audit
Authorization: Bearer <admin token>
Content-Type: application/json

{
  "apply_id": 12,
  "approve": true,
  "remark": "资料确认通过"
}
```

规则：

- 驳回时 `remark` 必填；
- 通过时备注可选；
- 锁定申请行并确认状态仍为待审核；
- 通过时在同一事务内创建商家、创建 `owner` 绑定并更新申请；
- 驳回时在同一事务内更新申请、审核人和审核时间；
- 重复或并发审核返回冲突，不得重复创建商家。

## 数据模型

本期沿用：

- `merchant_apply`：保存每次申请及审核历史；
- `merchant`：保存审核通过后创建的商家；
- `merchant_user`：保存普通用户与商家的角色绑定。

不新增业务表。状态值保持：

- `0`：待审核；
- `1`：已通过；
- `2`：已驳回。

创建待审核申请的查询与插入需要在事务边界内完成，继续利用 `(user_id, status)` 索引，并对并发重复请求返回同一条待审核申请。审核操作使用行锁保证申请状态转换和商家创建的一致性。

## 验证码安全

认证服务配置增加 `ExposeDebugCode`，默认值为 `false`。只有本地 Docker Compose 和明确的本地启动配置将其设置为 `true`。

- 开启时，发送验证码响应包含 `debug_code`；
- 关闭时，响应中省略 `debug_code`；
- 前端只在字段存在时展示；
- 验证码继续使用已有动态生成、有效期、消费次数和风控限制，不改为固定验证码。

## 错误处理

- 表单提交失败时保留用户输入；
- 查询失败显示错误状态和重试按钮；
- 待审核期间禁止重复提交；
- 审核冲突后管理员页面重新加载最新状态；
- 审核通过但绑定尚未读取到时显示初始化状态，不绕过权限守卫；
- 商家停用时不展示重新申请入口；
- 普通用户访问管理员接口返回无权限；
- 不在浏览器持久化申请草稿或验证码。

## 验收标准

### 新用户注册

- `/merchant` 可以切换登录和注册；
- 本地发送验证码后显示动态调试验证码；
- 错误验证码不能注册，正确验证码注册成功并自动登录。

### 提交申请

- 未绑定用户看到申请表；
- 提交后立即进入待审核状态；
- 刷新页面后恢复相同状态；
- 重复点击不产生两条待审核申请。

### 管理员审核

- `/admin` 出现“商家入驻”菜单；
- 管理员可以筛选申请并查看完整审核信息；
- 驳回原因必填；
- 通过或驳回后表格刷新且不能再次处理。

### 驳回重提

- 商家端显示驳回原因；
- 上次申请信息自动回填；
- 修改后产生一条新的申请记录；
- 管理员仍可查看旧申请历史。

### 通过与经营权限

- 通过后刷新状态可以进入经营后台；
- 新商家只能访问自己名下的数据；
- 停用商家不能进入经营页面，也不会看到重新申请表。

### 环境安全

- 本地配置开启时响应包含 `debug_code`；
- 配置关闭时响应不包含 `debug_code`；
- 普通用户不能访问管理员审核接口；
- 用户不能查询其他用户的申请。

## 验证策略

只增加与本功能直接相关的后端 handler/logic 检查和前端组件检查，不扩张或重构整套测试体系。实现完成后使用 Chrome 实际执行一次：

```text
注册新账号 → 提交申请 → 管理员查看并通过 → 新账号进入商家后台
```

再补充一条驳回后重新申请链路，以及关闭 `ExposeDebugCode` 后响应不泄露验证码的环境检查。
