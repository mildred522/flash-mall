# 平台后台与商家后台独立入口设计

## 背景与问题

Hertz 迁移提交改为使用 `frontend/packages/admin` 的 React/Vite 源码生成后台单文件。该源码只覆盖平台管理员页面，没有迁移旧后台中的商家工作区，也没有迁移商品 `image_url`、图片预览和文件上传控件。Hertz 后端仍保留图片上传、上传文件访问以及商家商品、库存、订单和退款接口，因此本次工作是补齐前端入口和权限边界，而不是回退 Hertz。

旧 `main` 的“平台后台 / 商家后台”只是同一 `/admin` 页面内的工作区切换，并不是真正独立应用。新实现将两者拆成独立入口，避免平台权限与商家权限继续由一个前端状态变量混用。

## 目标

- `/admin` 是平台运营后台，只接受平台管理员身份。
- `/merchant` 是商家后台，只接受已绑定且启用的商家身份。
- 平台后台保留当前 React 后台的跨商家商品、订单、退款、供应商、促销、用户、安全、对账和商家审核能力。
- 商家后台首期包含数据概览、商品、自定义图片、库存、订单发货和退款查看。
- 商品图片既可填写 URL，也可上传本地图片；上传成功后写入商品 `image_url`，商城目录立即使用该地址。
- 两个入口共用认证存储、API 客户端、领域类型和可复用的图片控件，但各自拥有独立路由、菜单和权限守卫。

## 非目标

- 本轮不把供应商和促销配置开放给商家。现有数据模型和接口是平台级，尚无可靠的商家归属字段；直接复用管理员接口会破坏租户隔离。
- 不恢复旧的 workspace 切换器。
- 不修改库存写链路的 Kitex 决策，也不改变商品读取继续走快照/缓存的架构。
- 不为拆分后台引入新的前端框架、微前端容器或独立部署域名。

## 路由与权限边界

| 入口 | 前端权限检查 | API 前缀 | 数据范围 |
| --- | --- | --- | --- |
| `/admin` | `/api/auth/me` 返回 `admin` | `/api/admin/*` | 全平台 |
| `/merchant` | 登录有效且 `/api/merchant/me` 返回至少一个启用商家 | `/api/merchant/*` | 当前身份绑定商家 |

Hertz 新增 `/merchant` 与 `/merchant/*any` 静态页面路由，返回独立的 `merchant.html`。API 仍由服务端中间件执行最终鉴权；前端守卫只负责用户体验，不能替代后端权限检查。

商家图片上传新增 `POST /api/merchant/products/image`，复用现有文件格式、大小、随机文件名和上传目录策略，但由 `RequireMerchant` 保护。商品创建和更新继续由既有商家处理器校验商家归属；上传文件本身不授予商品访问权。

## 前端结构

新增 `frontend/packages/merchant`，使用与 `admin` 相同的 React、Ant Design 和单文件 Vite 构建方式。它包含：

- `MerchantGuard`：验证登录状态与 `/api/merchant/me`。
- `MerchantLoginPage`：使用普通账号登录，不提供管理员演示登录按钮；登录后再次验证商家绑定。
- `DashboardPage`：读取 `/api/merchant/dashboard/stats`。
- `ProductsPage`：读取和修改当前商家的商品，支持图片 URL、上传、缩略图、创建、更新和库存调整。
- `OrdersPage`：读取当前商家订单，只开放服务端允许的发货操作。
- `RefundsPage`：只读展示当前商家退款。
- `InventoryPage`：读取商家库存变更记录。

共享包增加最小的图片上传函数与图片字段组件。管理员 `ProductsPage` 同时接入该组件，恢复平台后台的图片上传、图片预览以及创建/更新时的 `image_url` 传递。管理员和商家页面只通过配置选择各自上传及商品 API，不通过运行时 workspace 状态切换权限。

## 图片数据流

1. 用户选择本地图片或输入外部图片地址。
2. 本地图片以 `multipart/form-data` 上传到身份对应的 `/api/{admin|merchant}/products/image`。
3. Hertz 校验请求大小、文件类型和扩展名，将文件写入持久化上传目录并返回 `/uploads/products/<name>`。
4. 前端将返回地址显示为预览，并在商品创建或更新请求中提交 `image_url`。
5. 商品处理器写入 `mall_product.product.image_url`，随后触发既有商品卡片快照刷新。
6. 商城目录优先使用显式 `image_url`；图片加载失败时保留现有回退图逻辑。

只允许常见 Web 图片类型，继续执行 5 MB 上限。前端验证用于即时反馈，服务端验证是可信边界。上传失败、格式不支持或超限时，商品表单保持打开且不提交商品变更。

## 构建与交付

`frontend/build.js` 增加 merchant 构建目标，并将产物复制为 `app/entry/api/internal/handler/web/merchant.html`。默认完整前端构建同时生成 shop、admin 和 merchant；单目标命令可独立构建以缩小迭代范围。

`scripts/ci/check-web-artifacts.mjs` 扩展到 merchant，防止再次提交语法损坏或缺失的单文件产物。Docker 仍只嵌入已生成的静态页面，不在运行时安装 Node 依赖。

## 错误处理

- 未登录：显示对应登录页。
- 登录但不是管理员：`/admin` 拒绝进入，不降级为商家模式。
- 登录但没有启用商家：`/merchant` 显示无可用商家提示，不暴露平台后台入口。
- API 返回 401/403：清理失效身份并回到登录或无权限状态。
- 图片上传失败：展示服务端错误，保留已填写的其他商品字段。
- 商家操作非自有商品：以后端 404/403 为准，前端刷新列表，不尝试跨商家回退。

## 测试与验收

实现遵循测试先行。至少覆盖：

- 管理员商品表单上传图片并把 `image_url` 写入创建/更新请求。
- 商家守卫拒绝普通用户，接受具有商家绑定的登录用户。
- 商家页面只调用 `/api/merchant/*`，不存在 `/api/admin/*` 请求。
- 商家图片上传路由要求商家身份，并沿用大小和类型校验。
- Hertz 能分别返回 `/admin` 和 `/merchant` 两个不同页面。
- shop、admin、merchant 三个单文件产物均通过 JavaScript 语法检查。
- Chrome 实际链路验证管理员上传、商家上传、商城展示，以及两种身份互相越权时被拒绝。

验收结果应证明：两个后台入口和菜单彼此独立；平台管理员能力不回退；商家只能操作自己的数据；自定义图片从上传到商城展示形成完整闭环。

## 迁移策略

先增加共享图片能力并恢复管理员图片功能，再新增商家入口，最后接入 Hertz 路由、构建产物和桌面控制中心入口。每一步都保持 `/admin` 可用。旧单文件 workspace 仅作为行为参考，不重新成为运行时依赖。
