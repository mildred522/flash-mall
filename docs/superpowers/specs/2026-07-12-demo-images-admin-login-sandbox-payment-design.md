# 商品图片、管理员快捷登录与沙箱扫码支付设计

## 目标

在 Hertz 主入口上完成三项可直接演示的能力：稳定显示商品图片、从管理控制台一键登录演示管理员、用二维码完成一笔具有完整幂等证据链的沙箱支付。实现必须复用当前 Go-zero 订单 RPC、Kitex 库存命令、支付回调、outbox 和 RabbitMQ 链路，不新增仅为统一技术栈而产生的同步跳数。

## 当前问题与约束

商品图片故障由两个确定问题叠加产生：`mall_product.product.image_url` 中的演示商品值为空，且 React `ProductCard` 没有渲染响应中的 `image_url`。当前上传目录也为空，因此不能把 emoji 回退误认为图片功能正常。

管理员快捷登录暂时直接显示在控制台登录页，不在本阶段实现环境开关。它复用正式密码登录接口，不新增免密后门接口。

当前 `/api/order/pay` 会直接构造 mock 回调并把订单改为已支付，无法表现支付意图、扫码端、异步回调和重复通知。本阶段将其改为拉起沙箱支付，不接入需要真实商户资质的微信或支付宝。

## 总体架构

商品读路径保持 `Hertz -> product-rpc/product_card_snapshot`。图片元数据继续由 Hertz 从商品主表补齐，前端负责图片加载回退。演示图片作为前端构建产物随 Hertz 镜像发布；管理员上传图片仍保存到宿主机绑定的 `.runtime/uploads`。

管理员快捷登录只在前端触发现有 `/api/auth/login`，账号为 `13800000002`，密码为当前演示密码 `flashmall123`。成功后沿用现有 access token、refresh token 和 `AdminGuard`，因此权限校验仍由 JWT 角色与 Hertz 管理员中间件完成。

支付以现有 `payment_order` 作为支付意图的唯一事实来源。Hertz 生成短期签名的扫码令牌，付款页确认后进入统一的支付结果处理函数，再调用 Order RPC 的 `MarkOrderPaid`。订单 RPC 继续负责支付单、订单状态、回调事件、库存确认和 `order.paid` outbox 的事务与幂等控制。

## 商品图片设计

### 数据与资源

- 为商品 100–104 提供五张项目内置演示图，放入商城前端的 public 商品资源目录并随构建产物复制到 Hertz Web 目录。
- Hertz 注册只读商品资源路由，路径与上传资源分离，避免把镜像内置资源误认为运行时上传文件。
- 初始化 SQL 为 100–104 设置内置图片 URL，并在重复执行时恢复演示商品的稳定 URL。
- 管理员上传成功后仍把 `/uploads/products/<name>` 写入 `product.image_url`，该值优先于内置回退图。

### 前端回退顺序

`ProductCard` 按以下顺序显示：

1. API 返回的非空 `image_url`。
2. `PRODUCT_META` 中对应商品的内置图片 URL。
3. 图片请求失败时显示现有 emoji。

图片元素使用商品名称作为 `alt`，保留懒加载，并在加载失败后隐藏损坏图片。订单卡片使用同一图片解析函数，避免商品页和订单页表现分叉。

快捷登录调用体为：

```json
{
  "phone": "13800000002",
  "password": "flashmall123"

```

按钮在请求期间禁用，失败时显示明确的演示账号登录错误，不吞掉服务端失败。因为没有新增后端接口，攻击面不超过当前已经公开的演示账号密码登录能力。生产开关和演示凭据注入属于后续控制台配置治理范围。

## 沙箱扫码支付设计

### API

`POST /api/order/pay` 改为创建或获取支付意图，请求保持 `order_id`，响应扩展为：

```json
{
  "order_id": "order-id",
  "payment_order_id": "pay:order-id",
  "out_trade_no": "mock-order-id",
  "payable_amount_fen": 9900,
  "status": "pending",
  "qr_url": "http://host:8889/pay?token=...",
  "expires_at": 1780000000
}
```

相同用户对相同订单重复调用时返回同一 `payment_order_id` 和 `out_trade_no`。二维码令牌可以因时间窗口重新签发，但不能改变支付事实。

新增 `GET /pay` 作为独立付款页。页面解析令牌后展示订单号、金额、剩余有效期和确认按钮，不要求扫码设备登录商城账号。

新增 `POST /api/payment/sandbox/confirm`。请求仅携带签名令牌；服务端验证签名、有效期及令牌字段与数据库支付单完全一致，然后生成稳定事件号 `sandbox:<payment_order_id>`，进入统一支付结果处理。

新增 `GET /api/payment/status`，支持两种互斥的查询方式：商城端携带登录态和 `payment_order_id`，且只能查询自己的支付单；付款页不携带登录态而提交完整 `token`，服务端验证签名后只查询令牌绑定的支付单。响应包含 `pending`、`paid` 或 `expired`，其中 `expired` 由未支付令牌超过有效期推导，不修改支付单事实状态。

现有 `POST /api/payment/callback` 保留给外部 provider，签名校验后与沙箱确认复用同一个内部处理入口。

### 令牌

令牌包含 `order_id`、`payment_order_id`、`out_trade_no`、`payable_amount_fen` 和 `expires_at`，使用现有支付回调 secret 派生的 HMAC-SHA256 签名。服务端不接受令牌覆盖数据库金额，所有字段必须与 `payment_order` 匹配。默认有效期为十五分钟。

二维码 URL 基于当前浏览器 origin 生成，因此用局域网 IP 打开商城时手机可以实际扫描；使用 `localhost` 打开时只能由本机浏览器模拟扫码。界面同时提供“在本机打开付款页”，确保没有手机时也能完整演示。

### 幂等证据链

1. 创建订单由 `orders.request_id` 唯一约束保证幂等。
2. 支付意图由 `payment_order.order_id` 和 `out_trade_no` 唯一约束保证幂等。
3. 沙箱付款为每个支付单生成固定 provider 事件号。
4. `payment_callback_event` 对 provider 与事件号建立唯一约束，重复确认只读取第一次处理结果。
5. 支付单和订单使用待支付到已支付的条件更新；已支付请求返回成功而不重复执行业务。
6. Kitex `ConfirmDeduct` 继续按订单幂等，重复调用不重复扣减。
7. `order.paid` outbox 使用稳定事件标识，RabbitMQ 重投不产生重复投影。

商城支付弹窗在发起后轮询状态。首次确认和重复确认都显示已支付，但管理后台能从支付回调事件、订单状态日志和 outbox 记录中看到只有一次有效状态变更。

## 错误处理

- 非订单所有者拉起支付或查询状态返回未授权或未找到，不泄露支付单信息。
- 已取消、已关闭或已退款订单不能重新拉起支付。
- 金额不一致、字段不一致、签名无效或令牌过期均拒绝确认，订单保持待支付。
- 支付确认过程中 Order RPC 不可用时返回可重试错误；同一令牌重试仍使用相同事件号。
- 二维码过期后商城可以重新获取支付意图并生成新令牌，不创建第二张支付单。
- 商品图片请求失败不影响商品购买，前端降级为 emoji 并保留可访问文本。

## 测试与验收

实现遵循测试先行：先让组件、签名令牌、支付意图所有权、重复确认和图片回退用例失败，再编写最小实现。

最终验收包含：

- 初始化数据库后五个演示商品均返回非空图片 URL，图片请求为 200，商城和订单卡片都能显示。
- 管理员快捷登录一次点击进入控制台，普通表单登录仍可用，非管理员 token 仍被 `AdminGuard` 拒绝。
- 创建订单后付款按钮展示二维码；另一浏览器或手机打开付款页并确认后，商城自动显示已支付。
- 对同一付款令牌连续确认至少三次，订单只变更一次、库存只确认一次、`order.paid` outbox 只有一个有效业务事件。
- 篡改金额、支付单号或过期时间的令牌被拒绝，订单与库存不变。
- 执行相关前端测试、Go 包测试、全仓 `go test ./...`、前端构建、Docker 定向重建和真实 HTTP 链路验证。
