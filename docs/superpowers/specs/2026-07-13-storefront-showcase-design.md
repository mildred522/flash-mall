# 商家店铺与首页商品橱窗设计

日期：2026-07-13

状态：设计已确认，等待实施计划

## 1. 背景

当前商城首页通过 Hertz 的 `/api/shop/catalog` 读取商品。当请求不带筛选条件且配置了 `CatalogProductIDs` 时，网关直接返回固定的 `100～104` 五件演示商品。商家后来创建并上架的商品虽然满足可售条件，也能通过 `/api/shop/products` 查询，但不会出现在首页。

问题的本质不是商品创建、图片上传或库存同步失败，而是现有模型把“首页目录”实现成了固定配置，且没有区分以下三个概念：

1. 商品是否可售；
2. 商品是否展示在所属商家的店铺；
3. 商品是否获得平台首页曝光。

本设计引入统一模板商家店铺和独立的首页商品橱窗，使商品经营权与平台曝光权分离。

## 2. 目标

- 每个启用商家拥有一个公开店铺页面。
- 商家决定哪些商品在自己的店铺上架销售。
- 商品上架后立即进入本店页面，但不会自动进入商城首页。
- 平台管理员逐件选择进入首页橱窗的商品。
- 首页固定提供 12 个橱窗位置，同一商家最多占 2 个位置。
- 推荐算法为管理员提供可解释的候选排序，但不自动发布商品。
- 商品、店铺或库存失效后，首页自动停止展示，管理员后台保留待补位提示。
- 首页商品、商品详情和商家店铺之间形成双向可导航链路。
- 保持现有 Go-zero 商品读链路、`product_card_snapshot` 快照和 Kitex 库存写链路不变。

## 3. 非目标

第一版不实现以下能力：

- 商家拖拽装修店铺；
- 自定义店铺主题、颜色和区块顺序；
- 基于用户画像的个性化推荐；
- 推荐算法自动发布或自动补位；
- 独立推荐微服务、模型训练和特征平台；
- 多套橱窗、分人群橱窗或定时活动橱窗；
- 首页曝光计费或广告竞价。

## 4. 已确认的产品规则

### 4.1 店铺模板

所有商家使用统一店铺模板。商家可维护：

- 店铺头像；
- 店铺横幅；
- 店铺简介。

店铺名称、联系人和启用状态继续来自现有 `merchant` 表。未填写扩展资料时使用默认头像、默认横幅和空简介，店铺仍可正常访问。

### 4.2 商品上架

- 状态为上架的商品出现在所属商家的公开店铺中，并允许购买。
- 状态为下架的商品不在店铺中展示，也不允许继续购买。
- 商品上架不自动获得首页曝光。
- 店铺商品列表直接查询现有商品数据，不复制商品记录。

### 4.3 首页橱窗

- 首页固定 12 个槽位。
- 管理员按具体商品选择橱窗内容。
- 同一商品不能重复出现。
- 同一商家最多占 2 个槽位。
- 管理员可以调整槽位顺序。
- 管理员一次发布完整布局，发布前的调整只保存在浏览器草稿中。
- 首页只读取管理员已经发布的布局。

### 4.4 失效处理

橱窗商品出现以下任一情况时，公开首页立即跳过该商品：

- 商品已下架；
- 所属店铺已停用；
- 可售库存为零；
- 商品或店铺已不存在。

系统不自动选择替代商品。管理员后台保留原槽位和商品信息，并显示具体失效原因及“待补位”状态，直到管理员手动移除或替换。

## 5. 领域边界

### 5.1 商家店铺

负责公开展示店铺资料与该商家的启用商品。店铺资料归商家维护，商家只能修改自己绑定店铺的数据。

### 5.2 商品经营

继续负责商品名称、图片、价格、供应商、上下架状态和库存操作。库存写命令继续走 Kitex，商品读模型继续使用 Go-zero product-rpc 和商品卡片快照。

### 5.3 平台橱窗

负责首页固定槽位、发布版本、管理员操作和失效展示。橱窗不改变商品自身状态。

### 5.4 推荐候选

负责从全站可售商品中计算管理员候选排序。它是只读决策辅助，不拥有发布权限，也不进入首页请求链路。

## 6. 数据模型

### 6.1 `merchant_store_profile`

存放于商家数据所在数据库，与 `merchant` 一对一：

| 字段 | 类型/约束 | 含义 |
|---|---|---|
| `merchant_id` | bigint，主键 | 商家 ID |
| `logo_url` | varchar(512) | 店铺头像 |
| `banner_url` | varchar(512) | 店铺横幅 |
| `description` | varchar(1000) | 店铺简介 |
| `version` | bigint，非空 | 乐观版本号 |
| `create_time` | timestamp | 创建时间 |
| `update_time` | timestamp | 更新时间 |

更新资料时校验图片 URL 必须来自允许的本地上传目录或合法的 HTTP(S) 地址。简介在服务端去除首尾空白并限制长度。

### 6.2 `mall_product.homepage_showcase`

全局只保留一条当前橱窗记录：

| 字段 | 类型/约束 | 含义 |
|---|---|---|
| `id` | bigint，主键，固定为 1 | 当前首页橱窗 |
| `version` | bigint，非空 | 发布版本 |
| `operator_id` | bigint | 最后发布管理员 |
| `publish_time` | datetime | 最后发布时间 |
| `update_time` | timestamp | 更新时间 |

### 6.3 `mall_product.homepage_showcase_item`

| 字段 | 类型/约束 | 含义 |
|---|---|---|
| `showcase_id` | bigint | 对应橱窗，第一版固定为 1 |
| `slot_no` | tinyint，1～12 | 槽位编号 |
| `product_id` | bigint，非空 | 商品 ID |
| 主键 | `(showcase_id, slot_no)` | 一个槽位只有一件商品 |
| 唯一键 | `(showcase_id, product_id)` | 同一商品不能重复 |

失效状态不写入明细表。服务端根据商品、商家和库存当前状态动态计算 `valid` 与 `invalid_reason`，因此不会出现衍生状态长期不同步的问题。

### 6.4 建表策略

- 初始化 SQL 增加正式表结构和前五个演示槽位。
- Hertz 保留幂等的 schema ensure 逻辑，兼容已有本地数据卷。
- `mall_product.product` 增加 `create_time timestamp`，用于新品评分；新商品默认写入当前时间。
- 迁移时已有商品统一回填为迁移时间之前 31 天，避免五件演示商品被误判为新品。
- 建表和种子写入都必须可重复执行。
- 不删除或重建现有商品、订单、商家和库存表。

## 7. 页面与导航

现有 `/products/*` 已用于内置商品图片静态资源，公开页面使用单数路径避免冲突：

- `/shop`：商城首页；
- `/product/{product_id}`：商品详情；
- `/store/{merchant_id}`：公开商家店铺。

Hertz 为 `/product/*any` 和 `/store/*any` 返回商城单页应用 HTML，再由前端读取路径参数。

用户导航规则：

1. 点击首页商品主体进入商品详情；
2. 点击首页商品卡片的店铺名称进入商家店铺；
3. 商品详情提供“进入店铺”按钮；
4. 店铺商品卡片进入商品详情；
5. 商品详情展示少量同店其他商品，但不执行个性化推荐。

## 8. API 设计

### 8.1 公开接口

#### `GET /api/shop/catalog`

读取已发布橱窗，按 `slot_no` 排序，只返回当前有效商品。每个商品卡片增加：

- `slot_no`；
- `merchant_id`；
- `merchant_name`；
- `store_url`。

返回的 `total` 表示当前实际可见商品数，不固定为 12。

#### `GET /api/shop/products/detail?product_id={id}`

扩展现有商品详情响应，增加：

- `merchant_id`；
- `merchant_name`；
- `store_url`；
- `store_status`。

商品不存在、商品已下架或店铺已停用时返回 404。库存为零时仍允许查看详情，但购买按钮禁用并显示售罄。

#### `GET /api/shop/stores/detail?merchant_id={id}`

返回店铺名称、头像、横幅、简介、启用状态和启用商品数。店铺不存在或停用时返回 404。

#### `GET /api/shop/stores/products`

查询参数：

- `merchant_id`，必填；
- `page`，默认 1；
- `page_size`，默认 20，最大 100；
- `keyword`，可选。

只返回该商家的启用商品。

### 8.2 商家接口

#### `GET /api/merchant/store/profile`

返回当前登录商家的店铺资料和默认值。继续复用现有商家身份中间件。

#### `POST /api/merchant/store/profile`

请求包含 `logo_url`、`banner_url`、`description` 和 `expected_version`。服务端根据登录身份确定 `merchant_id`，不接受客户端指定其他商家。

版本不匹配时返回 409，并保留客户端当前表单内容。

#### `POST /api/merchant/store/assets`

上传店铺头像或横幅，沿用现有商品图片的文件类型、大小、随机文件名和路径穿越防护。文件保存到 `/uploads/stores/`，接口返回公开 URL。

### 8.3 管理员接口

#### `GET /api/admin/showcase`

返回：

- 当前橱窗版本；
- 最后操作人和发布时间；
- 1～12 槽位；
- 每个槽位的商品、商家、库存和有效性；
- 失效槽位的 `invalid_reason`。

允许的失效原因：

- `product_not_found`；
- `product_inactive`；
- `merchant_not_found`；
- `merchant_inactive`；
- `out_of_stock`。

#### `GET /api/admin/showcase/candidates`

支持 `page`、`page_size`、`keyword` 和 `merchant_id`。返回满足候选条件的商品、分项评分、总分和中文推荐原因。

默认排除已经进入橱窗的商品，以及已有 2 个有效橱窗商品的商家。

#### `POST /api/admin/showcase/publish`

请求结构：

```json
{
  "expected_version": 3,
  "items": [
    { "slot_no": 1, "product_id": 105 },
    { "slot_no": 2, "product_id": 102 }
  ]
}
```

允许 `items` 少于 12 条，缺失位置视为空槽位。服务端在事务中：

1. 锁定 `homepage_showcase`；
2. 比较 `expected_version`；
3. 重新读取并校验所有商品、店铺和库存状态；
4. 校验槽位范围、商品唯一和单商家最多 2 件；
5. 替换全部明细；
6. 版本加一并记录操作人；
7. 提交事务；
8. 写入管理员审计事件。

任一校验失败时不修改现有橱窗。

## 9. 推荐算法

### 9.1 候选资格

候选商品必须同时满足：

- 商品状态为启用；
- 所属商家状态为启用；
- 商品可售库存大于零；
- 商品不在当前橱窗中；
- 该商家当前有效橱窗商品少于 2 件。

### 9.2 评分

总分最高 100 分：

| 因素 | 分值 | 说明 |
|---|---:|---|
| 近 7 天销量 | 0～40 | 使用已支付商品数量，按确定的销量区间评分 |
| 库存充足度 | 0～15 | 按确定的库存区间评分，库存为零已在资格阶段排除 |
| 有效促销 | 0～10 | 当前存在生效促销时加分 |
| 商品新鲜度 | 0～20 | 7 天内最高，8～30 天递减，30 天后为零 |
| 商家多样性 | 0～15 | 当前橱窗该商家为 0 件时最高，已有 1 件时降低 |

同分时按近 7 天销量、商品创建时间和商品 ID 依次降序，保证结果稳定。

具体分段固定如下：

- 近 7 天销量：0 件为 0 分，1～2 件为 8 分，3～5 件为 16 分，6～10 件为 24 分，11～20 件为 32 分，21 件及以上为 40 分；
- 可售库存：1～5 件为 3 分，6～20 件为 7 分，21～50 件为 11 分，51 件及以上为 15 分；
- 有效促销：存在当前生效促销为 10 分，否则为 0 分；
- 商品新鲜度：创建 7 天内为 20 分，8～14 天为 14 分，15～30 天为 7 分，超过 30 天为 0 分；
- 商家多样性：当前有效橱窗为 0 件时为 15 分，已有 1 件时为 6 分，已有 2 件时不进入候选。

### 9.3 推荐原因

候选响应必须给出可解释原因，不只返回总分。例如：

- `近7天销量36件`；
- `库存充足`；
- `当前有限时促销`；
- `7天内新品`；
- `该商家当前未获得首页曝光`。

### 9.4 计算位置

- 评分只在管理员候选接口中执行。
- 可对候选结果缓存 60 秒。
- 首页请求不执行推荐算法。
- 推荐计算失败不影响当前首页，管理员仍可使用搜索手动选品。

## 10. 前端设计

### 10.1 商城首页

- 保留现有首页整体结构。
- “热销商品”数据源切换为已发布橱窗。
- 商品卡片主体进入详情页。
- 商品卡片增加可点击的店铺名称。
- 只渲染有效橱窗商品；不足 12 件时不补假数据。

### 10.2 商品详情页

- 展示图片、名称、价格、促销、库存和购买入口。
- 库存为零时显示售罄并禁用购买。
- 展示商家名称和“进入店铺”按钮。
- 展示少量同店启用商品。

### 10.3 公开店铺页

- 统一横幅、头像、名称和简介布局。
- 展示店内启用商品总数。
- 商品列表支持分页。
- 没有商品时显示明确空状态。

### 10.4 商家后台

新增“店铺设置”菜单：

- 编辑头像、横幅和简介；
- 上传店铺图片；
- 预览统一店铺模板；
- 保存成功后刷新版本。

商品管理继续只负责商品上下架，不增加首页推荐开关。

### 10.5 管理员后台

新增“首页橱窗”菜单：

- 上方或左侧显示 12 个固定槽位；
- 支持拖动排序、移除和替换；
- 失效槽位显示红色原因和待补位标记；
- 下方或右侧展示推荐候选表；
- 候选展示商品、商家、库存、销量、各分项分数和原因；
- 所有改动先进入本地草稿；
- 点击“发布橱窗”后原子生效；
- 版本冲突时保留本地草稿并提示重新加载。

## 11. 一致性与库存边界

- 商家上下架、管理员发布和首页读取都以商品状态为准。
- 店铺访问和橱窗资格都以商家当前状态为准。
- 首页库存展示和候选评分使用库存快照。
- 商家通过 Kitex 调整库存后，继续刷新库存快照和商品卡片快照。
- 快照存在短暂延迟是允许的；用户结算时仍以 Kitex 库存预占结果为最终依据。
- 橱窗读取不新增 Kitex 同步调用，避免给高频读路径增加 RPC 跳数。
- 橱窗失效是读取时派生结果，不在商品变更事务中跨库更新橱窗表。

## 12. 权限、安全与审计

- 公开店铺与商品接口不需要登录，但只返回启用对象。
- 店铺资料修改和资源上传必须通过商家身份校验。
- 管理员橱窗接口必须通过管理员身份校验。
- 服务端忽略商家资料请求中的外部 `merchant_id`，以登录身份为准。
- 上传资源限制 MIME、扩展名、大小和保存目录。
- 发布接口使用版本号防止并发静默覆盖。
- 发布成功记录管理员 ID、版本、商品列表和时间。
- 店铺资料修改记录商家 ID、用户 ID、结果和请求 ID。
- 日志不得记录令牌和上传文件内容。

## 13. 错误处理

- 公开店铺不存在或停用：404。
- 商品不存在、下架或店铺停用：详情接口 404。
- 商品售罄：详情可访问，但购买入口禁用。
- 店铺资源上传失败：不修改原有资料。
- 店铺资料版本冲突：409。
- 橱窗版本冲突：409，并返回当前版本。
- 发布商品状态已经变化：409，并返回槽位和原因。
- 推荐计算失败：候选接口返回错误，当前首页不受影响。
- 首页存在失效槽位：跳过该商品，不返回 5xx。

## 14. 旧数据迁移

部署顺序：

1. 创建店铺资料、橱窗和橱窗明细表；
2. 为商品表增加 `create_time`，已有商品回填为迁移时间之前 31 天；
3. 创建全局橱窗记录，初始版本为 1；
4. 将当前配置中的 `100～104` 写入槽位 1～5；
5. 槽位 6～12 保持为空；
6. 验证新橱窗接口返回与旧首页一致；
7. 首页切换为读取橱窗表；
8. 移除 `CatalogProductIDs` 对首页无筛选请求的覆盖逻辑；
9. 保留 `/api/shop/products` 作为全部启用商品查询接口。

迁移是幂等的：已有橱窗数据时不得重新覆盖管理员发布结果。

## 15. 可观测性

记录以下指标：

- 当前有效橱窗商品数；
- 待补位槽位数；
- 各失效原因数量；
- 橱窗发布成功率与冲突数；
- 推荐候选计算耗时和失败率；
- 店铺详情与店铺商品接口 p95；
- 首页橱窗接口 p95。

日志统一携带请求 ID。管理员发布日志同时记录橱窗版本和操作人。

## 16. 测试策略

### 16.1 后端单元测试

- 候选资格过滤；
- 五项评分和同分排序；
- 商品重复校验；
- 槽位范围校验；
- 单商家最多 2 件校验；
- 失效原因派生；
- 店铺资料权限和版本冲突；
- 橱窗版本冲突。

### 16.2 后端集成测试

- 发布事务全部成功或全部回滚；
- 发布后首页按槽位顺序返回；
- 商品下架、库存归零或店铺停用后首页自动跳过；
- 失效槽位仍在管理员接口中可见；
- 旧五件商品迁移保持不变；
- 商家不能修改其他店铺资料。

### 16.3 前端测试

- 首页商品与店铺链接跳转；
- 商品详情进入店铺；
- 店铺页只展示本店启用商品；
- 商家店铺资料上传、预览和保存；
- 管理员槽位编辑、排序、移除和发布；
- 单商家超过 2 件时的前端提示；
- 失效槽位和版本冲突提示。

### 16.4 端到端验证

完整链路：

1. 商家创建并上架商品；
2. 商品出现在本店但不在首页；
3. 管理员在推荐候选中看到商品和原因；
4. 管理员把商品加入空槽位并发布；
5. 首页出现商品和店铺入口；
6. 用户进入商品详情和店铺；
7. 商家下架商品或将库存降为零；
8. 首页隐藏商品；
9. 管理员看到待补位告警并选择替代商品。

5. 商家店铺设置页面；

## 18. 验收标准

- 商家能够维护统一模板店铺资料。
- 商家上架商品后立即出现在自己的店铺，但不会自动进入首页。
- 管理员能够查看带分数和原因的推荐候选。
- 管理员能够编辑 12 个槽位并原子发布。
- 同一商家超过 2 件时发布失败。
- 商品失效后首页自动隐藏，管理员后台显示待补位。
- 首页商品能够进入商品详情和商家店铺。
- 商品详情能够进入商家店铺。
- 两个管理员并发编辑不会静默覆盖。
- 原有 `100～104` 五件演示商品在迁移后继续展示。
- 首页读取不增加 Kitex RPC 跳数。
- 全量 Go 测试、前端测试、生产构建和 Docker 健康验证通过。
