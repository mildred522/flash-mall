## MySQL 写路径定位与优化复测

### 定位

在提交 `16b9141` 的失败边界，订单生命周期由 `cancel_order` 主导，完整交易由 `confirm_payment` 主导；MySQL CPU 分别达到 139.3% 和 147.9%，`Threads_running` 达到 42 和 43。Go CPU profile 的主要时间落在系统调用和数据库等待，不是某段 Go 计算逻辑。

进一步对 150 TPS、3,750 次订单闭环做 MySQL Performance Schema 采样：`COMMIT` 8,528 次，累计等待 140.302 秒，平均 16.452 ms。表级统计同时显示，每条 `order_outbox` 事件除插入和发布确认外，发布器还会逐条执行一次 `pending -> publishing` 抢占。配置虽然每批读取 200 条，抢占仍最多产生 200 个独立自动提交，形成了可消除的小事务放大。

这轮没有通过扩大连接池、降低 `innodb_flush_log_at_trx_commit` 或关闭业务一致性来换取数字。修改只作用于异步 Outbox 发布：

- Redis 单活锁开启时，一次读取的事件使用一条带 `status = pending` 条件的批量 CAS 更新完成抢占；最多 200 次抢占提交收敛为 1 次。
- 单活关闭时保留原逐条 CAS，避免多发布实例竞争时误领事件。
- 批量影响行数必须等于候选数，否则失败关闭；原有 publishing 超时恢复、RabbitMQ confirm、重试和死信状态机保持不变。

### 同参数诊断样本

在相同的 150 TPS、25 秒、并发 160 诊断样本中，修改前后 MySQL 显式提交次数相近（8,528 对 8,586），便于比较等待成本：

## 面试叙事

建议按“测量方法—证据—取舍—结果—下一步”讲，而不是只报一个最高 QPS：

1. **先修测试可信度。** 把公开读、订单创建/取消、创建/支付/确认完整交易拆成独立场景，区分业务 TPS 与一次交易内部的 HTTP QPS；同时覆盖基准、预期负载、闭环饱和、自动压力边界、稳定性和故障恢复，并把重复订单、负库存、悬挂预占、Outbox 残留、Redis/MySQL 一致性设为硬门禁。
2. **再用证据定位。** 失败边界不是 Hertz 或 Kitex 算力不足：Go profile 主要在系统调用/数据库等待，MySQL CPU 接近 1.5 核，running threads 超过 40，Performance Schema 又显示提交平均等待 16.452 ms；表级写入进一步暴露 Outbox 批量读取、逐条抢占的事务放大。
3. **优化时守住可靠性。** 没有调低 MySQL 刷盘级别，也没有盲目扩大连接池；利用已有 Redis 单活锁，把最多 200 次状态抢占收敛为一次批量 CAS，保留多实例模式的逐条安全路径、影响行数校验、超时恢复和 RabbitMQ confirm。
4. **结果不夸大。** 定位样本的提交平均等待下降 17.4%、p50 下降 58.7%，但完整套件的订单容量边界仍为 150/165 TPS，完整交易闭环峰值只波动 1.3%。这说明优化减少了异步辅助工作的数据库成本，却没有改变同步交易的临界路径，是一次符合 Amdahl 定律的局部优化。
5. **给出合理收尾判断。** 若继续追求写吞吐，下一步应减少同步链路中的持久化提交、拆分库存与订单的数据库资源、验证 DTM/支付确认事务的等待构成，而不是继续微调 Outbox。对于当前面试演示和可实际运行目标，保留一致性与可解释的容量边界比牺牲可靠性追求本机峰值更有价值。

一句话版本：**我先把压测从“固定 RPS 看成功率”升级为带业务不变量的容量测试，用 profile、MySQL 线程和提交等待定位写事务瓶颈；随后消除 Outbox 的逐条提交放大。局部提交等待下降约 17%，但端到端上限没有显著提高，最终确认真正瓶颈仍是同步交易的强一致持久化，并据此停止无效调参。**
