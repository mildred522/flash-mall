# Flash Mall 面试讲解手册

> 面向 Go 后端、微服务和分布式系统岗位。本手册只使用当前代码与已冻结的实测结果，不把本地容量实验包装成公网生产数据。

## 1. 面试前先记住的项目定位

Flash Mall 不是一个单纯的商城 CRUD 项目，而是一套可运行、可观测、可故障恢复的交易系统演进样例。项目保留 `main` 分支上的 Go-zero Entry API 基线，在 `codex/arch-hertz-kitex` 分支上把外部网关迁移到 Hertz，并将库存写命令收敛到 Kitex；商品读取继续走 Go-zero Product RPC 和读模型，支付后的非关键派生任务通过 MySQL Outbox 与 RabbitMQ 异步处理。

一句话版本：

> 我设计并实现了一个基于 Go 的分布式商城，重点解决下单库存一致性、支付幂等、事务消息、缓存穿透和故障恢复，并通过真实链路压测、Grafana 指标和 Jaeger Trace 验证架构取舍。

必须主动说明的边界：

- 当前是个人工程项目和本地 Compose 演示环境，不宣称拥有真实线上用户。
- `main` 是冻结的 Go-zero 基线，当前开发分支以 Hertz 为唯一新增外部 API 入口。
- Kitex 不是为了替换所有 RPC，只用于库存这一高频、稳定 IDL、强领域边界的写命令。
- 支付支持可重复演示的本地沙箱和支付宝开放平台沙箱，但没有接入真实商户生产资金。
- 容量结果来自 4 vCPU、约 8 GiB 的 Ubuntu WSL Docker 环境，结论只代表固定环境下“至少达到”的已测档位。

## 2. 30 秒开场

> Flash Mall 是我从 Go-zero 单体入口逐步演进出来的分布式商城。现在外部流量统一进入 Hertz，订单和商品仍复用 Go-zero RPC，库存预占、确认、释放使用 Kitex。下单采用 DTM SAGA 组织库存预占和订单创建，支付成功通过数据库行锁、唯一事件和状态机保证重复回调只生效一次，再把非关键工作通过 Outbox 和 RabbitMQ 异步化。读路径实现了 L1/L2 缓存、singleflight、陈旧值兜底、负缓存和 Redis Bitmap 布隆过滤器，最后用 Prometheus、Grafana、Jaeger、故障注入和真实链路压测验证一致性与容量。

## 3. 三分钟讲解版本

### 3.1 业务范围

系统包含商城、商家后台和统一管理员后台。用户可以浏览商品和店铺、下单、扫码完成沙箱支付、取消、申请退款和确认收货；商家可以申请入驻、维护店铺、上架商品、调整库存、发货和处理退款；管理员负责审核商家、管理商品和促销、发布首页橱窗、对账并观察系统事件。

### 3.2 架构分工

- Hertz 负责 HTTP 路由、身份透传、权限校验、响应协议和页面资源。
- Auth API 负责凭证、会话、验证码和安全审计。
- Product RPC 负责商品元数据和高频读路径。
- Order RPC 负责订单状态机、支付、退款、Outbox 与恢复任务。
- Inventory Kitex 负责库存预占、确认、释放、调整和对账。
- MySQL 保存订单、支付、库存账本和业务事实；Redis承载库存热数据与缓存；RabbitMQ承载支付后的异步派生事件。

### 3.3 最值得讲的正确性设计

创建订单时，Hertz发起 DTM SAGA：先调用 Order RPC 的库存预占分支，再创建订单；库存分支最终通过 Kitex调用 Inventory 服务。任何一步失败都会进入相应补偿，`order_id` 同时作为库存预占身份，重复请求不会重复扣减。

支付成功时，Order RPC锁定订单和支付单，在一个 MySQL事务中完成订单状态、支付状态、状态日志、回调事件和 `order.paid` Outbox事件。事务提交后再确认库存最终扣减；若 Kitex瞬时失败，支付仍保持成功，后台恢复任务继续完成库存确认，避免第三方反复回调造成重复入账。

### 3.4 性能和验证

项目不是只写了中间件配置。我实现了真实登录、公开读取、下单、库存预占、支付、幂等重放和 RabbitMQ故障恢复的容量工具。在固定 4 vCPU环境下，公开读最高已测档位约 594.68 QPS、8,921次请求全部成功，p95约 0.734ms；订单完整生命周期在 10 RPS档位149次全部成功，p95约123.464ms。实验结束后重复订单、重复支付回调、负库存、悬挂预占和 Outbox残留均为0。

## 4. 十五分钟现场演示

### 0-2 分钟：启动与健康检查

1. 在 Windows桌面控制中心选择“面试演示 + 可观测”。
2. 打开 `http://127.0.0.1:8889`，说明8889是 Hertz入口，8888只用于冻结的 Go-zero对比基线。
3. 运行发布就绪检查，展示34项只读检查全部通过。
4. 用一张拓扑图说明同步调用、异步事件和三类存储。

讲解重点：一键启动只是入口，真正价值是就绪检查会覆盖页面、图片、四个角色、两个商家隔离、Prometheus、Grafana、Jaeger和RabbitMQ，而不是只判断容器进程存在。

### 2-4 分钟：商城、商品和店铺

1. 展示首页六个橱窗商品。
2. 从商品进入详情和对应商家店铺。
3. 说明商家决定店内上架，管理员通过推荐候选和12槽橱窗决定首页曝光。
4. 指出商品图片是持久化上传素材，不是前端构建产物。

讲解重点：首页推荐只生成候选分数，最终发布由管理员决定；这避免把运营决策伪装成全自动算法。

### 4-7 分钟：下单、支付和幂等

1. 使用固定普通用户登录并创建订单。
2. 展示二维码和本地沙箱付款页。
3. 对同一支付令牌连续确认两次。
4. 回到订单列表确认状态只转移为一次“已支付”。
5. 在数据库或管理后台展示支付回调事件唯一、`order.created` 与 `order.paid` 各唯一、库存只确认一次。

讲解重点：幂等不是简单地在 Redis加一个锁。这里同时使用稳定业务键、数据库唯一约束、行锁、状态机和 `INSERT IGNORE` 事件记录；锁只减少竞争，数据库事实才是最终正确性边界。

### 7-9 分钟：商家隔离和管理员能力

1. 登录商家1101，只能看到山岚烘焙的店铺、商品和订单。
2. 登录商家1102，只能看到北纬三十六的数据。
3. 使用管理员入口展示商家审核、橱窗、订单、退款、对账和事件重试。

讲解重点：商家身份以 `mall_order.merchant_user` 为事实来源，商品写入还会在商品库中校验 `merchant_id` 所有权，不能仅依赖前端隐藏菜单。

### 9-12 分钟：缓存、消息和故障恢复

1. 展示商品缓存的 L1、Redis L2、软硬 TTL和singleflight。
2. 说明不存在商品如何经过负缓存和布隆过滤器提前拒绝。
3. 暂停 RabbitMQ故障演练时，支付事务仍完成，Outbox进入重试；RabbitMQ恢复后事件最终发布。
4. 说明库存预占过期、处理超时和死信如何进入恢复任务。

### 12-14 分钟：观测闭环

1. Grafana展示总览、库存一致性、支付与Outbox、缓存与RPC、容量与SLO五个面板。
2. Jaeger检索 Hertz、Order和Inventory业务Span。
3. 从同一个请求 ID或业务追踪 ID串起网关、订单和库存命令。

讲解重点：静态资源、健康探针和Prometheus抓取不会写入业务Trace，防止观测流量淹没真实链路。

### 14-15 分钟：迁移结论

> 我没有把所有服务机械迁到 Hertz或Kitex。Hertz承担外部网关，Kitex只收敛库存写命令，商品读继续保留 Go-zero RPC和缓存。成对实验中 Hertz真实目录响应更大，但两轮都没有出现性能回退；这个结果是端到端架构对比，不是框架微基准。

## 5. 架构取舍怎么讲

### 5.1 为什么从 Go-zero Entry API迁移到 Hertz

不要回答“因为 Hertz一定比 Go-zero快”。正确回答是：

> 原 Entry API把外部HTTP、业务编排、SQL查询、缓存和静态页面长期堆在同一层，迁移的主要目标是重建清晰的网关边界，同时保留 Go-zero在RPC、服务发现、熔断和工程生成方面的既有能力。Hertz适合高吞吐HTTP入口和中间件定制，迁移后我把新增外部API冻结在 Hertz，并通过application、ports和adapters逐域下沉业务与持久化访问。

迁移证据：

- Hertz生产Handler目录有架构测试，禁止出现 `database/sql`、裸SQL和事务代码。
- 商品、订单、商家、促销、橱窗等领域分别进入应用服务和MySQL适配器。
- 前端产物统一位于 `artifacts/web`，Hertz和冻结Entry基线都消费中立产物。
- 基线与候选分支使用独立worktree和固定提交进行成对实验，避免混淆两个分支。

### 5.2 为什么没有把所有RPC迁到Kitex

> 框架统一不是目标。Kitex适合高频、稳定IDL、强领域边界、需要连接治理的内部同步调用，所以库存预占、释放、确认和调整由Kitex统一承载。商品列表和详情是高频读路径，继续走已经稳定的Go-zero Product RPC、卡片快照和缓存，避免为了统一技术栈增加迁移风险与调用跳数。订单写命令继续由Go-zero Order RPC管理状态机和事务。

安全、鉴权、幂等和审计与传输框架无关。不能说“安全要求高用Kitex，安全要求低用原生RPC”，也不能只用一次微基准决定领域边界。

### 5.3 为什么同时使用同步RPC和消息队列

- RPC适用于调用方必须立即知道结果的工作：库存是否预占成功、订单是否创建成功、支付状态是否落库。
- MQ适用于主交易已经完成、可以稍后处理的派生工作：商品卡片刷新、库存审计、运营统计、搜索投影。
- 支付成功不等待RabbitMQ，否则消息系统故障会扩大成支付失败。
- Outbox解决“数据库提交成功但消息没发出去”的双写窗口，消费端去重解决重复投递。

### 5.4 为什么保留DTM SAGA

创建订单跨越库存和订单两个领域，无法使用一个本地事务覆盖。Hertz发起SAGA，正向分支是库存预占和订单创建，补偿分支是释放预占和回滚订单。DTM负责分支推进与Barrier，业务服务仍需自己实现幂等和空补偿。

支付成功不放进同一条SAGA：收款事实一旦在数据库持久化，就不能因为库存最终确认的瞬时失败向渠道返回失败。此时采用“支付成功事实优先 + 库存确认持久化重试”，比让第三方无限重放回调更安全。

## 6. 核心链路深挖

### 6.1 下单链路

1. Hertz从认证上下文取得用户身份，校验商品、数量、预期价格和请求ID。
2. 若请求ID已有订单，直接返回原结果。
3. Hertz生成稳定订单ID并向DTM提交SAGA。
4. `PreDeduct`分支通过Inventory Kitex执行 `ReserveStock`。
5. Inventory以 `order_id` 为预占身份，在Redis热库存和MySQL预占账本中保存结果。
6. `CreateOrder`分支锁定并验证商品快照、价格和商家信息，写订单、订单项、状态日志及 `order.created` Outbox。
7. 任一分支失败，DTM调用 `ReleaseStock` 或订单回滚；Release支持未执行正向分支时的空补偿和重复调用。

关键不变量：

- 同一请求ID只能对应一个业务订单。
- 同一订单预占不能更换商品或数量。
- 可用库存不能为负。
- 订单失败后不能留下长期悬挂预占。
- 商品当前名称或图片变化不能篡改历史订单快照。

### 6.2 库存链路

Inventory Kitex对外提供查询、批量查询、种子、调整、预占、确认、释放、对账和运行状态接口。Redis保存分桶后的可用库存，MySQL保存总量事实、预占账本、变更日志和快照。

为什么分桶：单个爆款商品如果只使用一个Redis Key，会把并发集中到同一热点。项目按订单ID确定起始桶，在Lua中轮询可用桶并原子扣减；这能分散热点，但不能凭空增加总吞吐，最终仍需以真实压测验证。

为什么要账本：仅有Redis幂等键无法回答“服务重启后这个订单到底预占过没有”。MySQL账本保存预占状态，Redis丢失时可以恢复，后台任务还能识别过期、处理中和死信预占。

### 6.3 支付链路

1. 用户请求创建支付单，Order RPC锁定订单并生成稳定支付身份。
2. 本地沙箱返回本机付款页；支付宝沙箱调用 `alipay.trade.precreate` 返回原生二维码内容。
3. 回调入口先验证签名、时间窗口、渠道、订单号和金额。
4. Order RPC对订单与支付单执行 `FOR UPDATE`，依据状态机决定首次成功、幂等回放、已关闭或金额不符。
5. 订单状态、支付状态、回调事件、状态日志和 `order.paid` Outbox在同一事务提交。
6. 事务提交后调用Kitex确认最终扣减；失败写入恢复状态，由后台重试。
7. Outbox发布 `order.paid`，消费者幂等更新卡片、库存审计、运营和搜索投影。

支付幂等的多层键：业务订单号、支付单号、外部交易号、渠道事件号、数据库状态机和唯一约束。Redis锁可以优化竞争，但不能替代这些持久化约束。

### 6.4 取消、超时和退款

- 待支付订单取消或超时时，先关闭渠道交易，再推进本地状态并释放库存。
- 支付恢复任务在截止前后主动查询渠道：已付款则补偿漏通知，未付款则关闭交易。
- 退款申请和审核通过订单状态机限制；渠道退款请求号稳定，重复审核不会重复退款。
- 渠道退款成功、库存释放和本地退款完成允许分阶段重试，避免一个瞬时故障破坏已经发生的资金事实。

### 6.5 Outbox链路

Outbox不是MySQL和MQ之间的中间件，而是项目在MySQL中实现的一种事务消息模式。业务事务将事件JSON写入 `order_outbox`；后台发布器竞争Redis领导锁，批量领取待处理事件并发布RabbitMQ。发布失败按次数和时间退避，超过上限进入dead状态，管理员可以观察和重试。

RabbitMQ中的消息本质是字节序列；本项目使用带 `event_id`、`event_type`、`order_id` 和业务载荷的JSON。消费者使用手动ACK，并以事件处理记录或投影事件表去重，因此允许至少一次投递而不重复产生业务效果。

## 7. 缓存问题怎么回答

### 7.1 缓存穿透

不存在的商品请求可能持续落到数据库。项目在L1/L2未命中并进入singleflight loader后，先检查短期负缓存，再检查Redis Bitmap布隆过滤器。ready generation明确判定不存在时直接返回；Redis或元数据异常时fail-open，避免过滤器故障误杀真实商品。

布隆过滤器按100万商品、1%假阳性率配置约9,585,059 bit和7次双哈希。它只回答商品ID是否可能存在，不承担上下架、库存、权限或店铺状态判断。新商品必须先写入过滤器再公开，重建时先构造新generation，完成后用Lua原子切换active generation。

### 7.2 缓存击穿

热点Key过期时，大量请求可能同时回源。项目用进程内singleflight合并同一Key的加载，并设置软TTL和硬TTL：软过期可以先返回旧值并由单个请求后台刷新，硬过期才同步等待回源；原点失败时允许在边界内返回陈旧值。

### 7.3 缓存雪崩

大量Key同一时间失效会形成回源洪峰。项目通过TTL稳定抖动、L1/L2不同生命周期、软硬TTL、后台刷新和陈旧值兜底分散过期时间。缓存失效事件经Redis Pub/Sub广播，其他Hertz实例只清除本地L1，不必等待自然过期。

### 7.4 Redis分布式锁在哪里体现

项目没有把分布式锁包装成万能正确性工具，主要用于：

- Outbox发布器领导权：`SET NX EX`取得租约，Lua比较owner后续租和释放，避免多个实例重复扫描同一批事件。
- 布隆过滤器重建：同一时刻只允许一个Hertz实例构建并切换新generation。
- singleflight只解决单进程并发，不属于分布式锁。

锁失效或进程暂停仍可能产生重复工作，所以Outbox领取使用状态条件更新，消费者还必须幂等；这就是“锁负责效率，数据库负责正确性”。

## 8. 可观测性和容量证据

### 8.1 指标

Hertz全局中间件记录固定低基数RED指标：请求数、耗时分布和在途请求。路由使用匹配后的模板而不是原始URL，未知API归为固定标签，防止商品ID、订单ID形成高基数时序。

业务指标覆盖库存预占状态、支付状态迁移、回调耗时、Outbox积压/发布/死信、缓存命中、布隆过滤器、素材完整性和RPC结果。Grafana预置五个面板，Prometheus配置5xx比例、p95、库存死信和Outbox积压等告警。

### 8.2 Trace

Hertz为业务API创建服务端Span，并传递请求ID、业务追踪ID、订单ID和幂等键。Order记录创建订单、支付意图和支付确认，Inventory记录reserve、confirm和release。健康探针、静态资源和Prometheus抓取不采样，避免Jaeger中只有噪声。

### 8.3 如何解释压测结果

推荐说法：

> 在4 vCPU、约8 GiB的固定WSL Docker环境和固定演示数据上，公开读混合场景最高已测600目标RPS，实际约594.68 QPS，8,921次全部成功，p95约0.734ms；订单完整生命周期最高已测10目标RPS，149次全部成功，p95约123.464ms。因为没有测到失败档位，所以我只说“至少达到当前档位”，不把它描述成系统上限。

Entry/Hertz对比推荐说法：

> 我使用冻结的 `origin/main` 和当前分支独立worktree，交替执行7轮、每轮60,000请求、并发30。Hertz目录返回6个商品和2,660字节，Entry返回5个商品和893字节，负载并不完全等价；结果显示Hertz中位QPS约高15.61%、p95约低16.9%，但p95变异系数超过预设阈值。因此结论只能是迁移后的真实读链路未观察到回退，不能宣称Hertz框架天然快15.61%。

## 9. 高频追问与建议回答

### Q1：为什么不用一个MySQL事务解决下单？

库存和订单属于不同服务边界，单个本地事务无法原子覆盖Redis、库存账本和订单库。SAGA接受中间状态，通过幂等正向分支和补偿实现最终一致；支付成功则使用本地事务固定资金事实，再异步完成外围工作。

### Q2：SAGA补偿失败怎么办？

补偿必须幂等、支持空补偿并留下持久化状态。Inventory保存预占账本，恢复任务处理过期、处理中和死信记录；监控悬挂预占与库存不一致，无法自动恢复时进入管理员对账入口。

### Q3：为什么库存既有Redis又有MySQL？

Redis承担原子、高频热路径，MySQL承担可恢复事实和审计。只用MySQL会让热点行锁成为瓶颈；只用Redis则难以在数据丢失、重启和长期审计时解释库存去向。

### Q4：为什么支付回调成功后库存失败仍返回成功？

第三方已经完成收款，本地订单和支付单也已事务提交。此时返回失败会导致渠道反复通知，却不能撤销资金事实。系统记录库存最终确认失败并持久化重试，同时通过指标和对账发现异常。

### Q5：Outbox会不会丢消息？

业务事实与Outbox在同一MySQL事务中，因此不会出现订单已提交但没有事件记录。发布器可能重复发送，但消费者按事件ID去重。真正需要防范的是数据库本身丢失，所以生产环境仍需要备份和高可用，而不是把Outbox描述成绝对不丢。

### Q6：Redis锁过期后两个发布器同时工作怎么办？

租约只降低并发扫描。领取事件还要带状态条件更新，RabbitMQ可能重复投递，消费者仍以事件ID幂等。即使锁在暂停期间过期，结果最多是重复工作，不能产生重复业务效果。

### Q7：布隆过滤器有假阳性怎么办？

假阳性只意味着一次请求继续访问缓存或原点，不会把不存在商品判断为存在；布隆过滤器没有假阴性才是关键。项目在未就绪和Redis异常时fail-open，避免元数据故障制造假阴性。

### Q8：缓存和数据库不一致怎么办？

写操作提交后精确清除相关Key并发布跨实例L1失效；读缓存设置短软TTL和有限硬TTL。缓存只加速商品展示，结算前以库存预占和订单内价格校验为准，因此短暂陈旧不会绕过交易正确性。

### Q9：为什么不把商品读取也改成Kitex？

现有Product RPC已经稳定，商品读还有L1/L2和卡片快照。迁移不会减少调用跳数，也没有证据说明它是瓶颈，反而扩大回归面。技术选型以领域边界和测量为依据，不追求框架统一。

### Q10：Hertz Handler是否直接访问数据库？

生产Handler不再包含裸SQL或事务，查询和命令分别进入application服务与adapters。一个需要说清楚的例外是创建订单Handler仍负责发起DTM SAGA编排，但实际库存和订单写入都由RPC分支完成。

### Q11：为什么用库存分桶，不直接对一个Key执行Lua？

单Key Lua虽然原子，但爆款请求仍集中到一个Redis执行点。分桶让不同订单从不同桶开始查找，降低单Key热点；代价是查询和对账更复杂，需要保证所有桶之和与MySQL事实一致。

### Q12：分桶会不会出现总库存够但每个桶都不够？

会。例如每个桶剩1件、一次请求需要2件时，总和可能足够但单桶无法满足。当前实现偏向单商品小数量电商场景，用简单分桶换取较低复杂度；若大批量订单成为主要场景，可以引入跨桶原子扣减Lua或按业务规格调整分桶策略。

### Q13：为什么还保留DTM，Kitex本身不能保证分布式事务吗？

Kitex是RPC框架，解决调用、序列化和连接治理，不负责跨服务业务事务。DTM负责SAGA分支编排和Barrier，Inventory与Order负责幂等、状态机和补偿语义，两者职责不同。

### Q14：支付为什么不用MQ直接驱动？

创建支付单和确认支付需要立即返回确定结果，适合同步RPC和本地事务。只有支付成功后的搜索、统计和卡片刷新才异步化；如果把核心资金状态完全交给MQ，会提高用户状态查询、超时处理和错误定位复杂度。

### Q15：RabbitMQ挂掉时会怎样？

订单和支付事务仍可提交，Outbox保留待发布事件。发布器记录失败、增加尝试次数并延后重试，恢复后继续投递。容量实验实际暂停RabbitMQ并验证恢复后Outbox在90秒窗口内清空。

### Q16：如何防止超卖？

下单前页面库存只是展示，不能作为交易依据。创建订单必须经过Inventory Kitex预占，预占由Redis Lua原子修改并写MySQL账本；相同订单重复调用幂等，支付后再确认最终扣减。容量实验结束还会检查负库存、悬挂预占和Redis/MySQL桶差异。

### Q17：如何保证历史订单图片不丢或不变？

下单时将商品名称、价格、图片URL和商家写入订单快照，查询订单不再依赖商品当前信息。上传文件以内容SHA-256命名并原子落盘，使用独立持久卷；前端图片组件仍提供加载失败降级。

### Q18：服务如何发现和治理？

Go-zero Product/Order RPC通过Etcd注册发现，并使用超时、熔断、统计和恢复中间件；Inventory Kitex当前使用显式内部Endpoint，重点演示稳定IDL、超时和调用元数据。公网只有Hertz入口，内部端口不应暴露。

### Q19：为什么不是Kubernetes生产部署？

仓库保留K8s清单用于展示部署边界，但当前实际演示使用单机Compose。单副本MySQL、Redis和RabbitMQ套上K8s并不会自动获得高可用，反而增加Ingress、存储和集群维护成本。真正上线会先采用生产Compose，再根据故障域和规模迁移托管数据服务或K8s。

### Q20：这个项目最大的不足是什么？

当前没有真实公网用户和生产支付流量，容量结论来自固定开发机；依赖仍以单节点Compose为主，上传素材使用本地持久卷；异步投影消费者仍有需要继续清理的运行时建表兼容逻辑。合理演进顺序是先完成生产Secret、TLS、备份和对象存储，再根据真实负载决定是否引入托管数据库和多节点部署。

## 10. 容易说错的话

| 不要这样说 | 应该这样说 |
| --- | --- |
| Hertz比Go-zero快15.61% | 两次端到端实验均未观察到迁移回退；一次实验中位QPS高15.61%，但负载和响应体不同且p95波动超过阈值 |
| 系统支持600 QPS | 固定环境公开读链路最高已测约594.68 QPS，未测到失败边界 |
| Outbox保证消息绝对不丢 | Outbox消除业务事务与事件记录之间的双写窗口，至少一次投递依赖消费者幂等，底层数据库仍需备份和高可用 |
| Redis分布式锁保证只有一个消费者 | 锁减少并发工作，条件更新、唯一约束和消费幂等保证业务正确性 |
| Kitex比gRPC安全或更快 | Kitex用于稳定的库存领域命令，安全与幂等由业务协议保证，性能必须按真实链路测量 |
| K8s让项目高可用 | 现有清单展示部署边界；状态依赖单副本时并不构成完整高可用 |
| 已接入支付宝支付 | 已接入支付宝开放平台沙箱协议和恢复流程，没有使用真实商户生产资金 |
| 我解决了CAP | 我针对具体链路选择强一致本地事务、SAGA最终一致和Outbox至少一次投递，并明确失败处理 |

### 现场故障优先级

1. 页面打不开：先展示发布就绪检查和架构图，不在面试中长时间修环境。
2. 图片失败：刷新一次并说明素材持久卷与完整性指标，切换到预先打开的页面。
3. 支付失败：展示已有订单、数据库唯一事件与Grafana面板，口述首次回调和幂等回放。
4. Grafana无数据：先执行一次商品读取和下单，再刷新；仍无数据则展示冻结容量JSON。
5. 整体Docker失败：使用预录演示视频和本手册中的真实结果，重点讲设计与取舍。

## 12. 最后的收束表达

> 这个项目让我真正理解了微服务不是把代码拆成多个进程。服务边界必须对应数据所有权，RPC和MQ要根据结果是否进入同步条件来选择，幂等要落到稳定业务身份和数据库约束，缓存不能参与最终交易判断，观测和故障演练也必须覆盖真实链路。相比最初的Go-zero版本，现在最大的提升不是多用了Hertz和Kitex，而是把这些技术选择变成了可以解释、可以验证、可以恢复的系统设计。
